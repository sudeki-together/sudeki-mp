## Native test-arena harness

The supported build ships a developer `testroom` level, test-room scene-map resources, and a `Training_Dummy`. Sudeki's own `DoOneLevelTest()` startup path consumes `-Level testroom`, so `--cleanroom`/`--test-arena` can enter it without repacking `SOLData.baf` or patching `SUDEKI.exe`. Live testing confirmed sparse floor/wall geometry loads without a save. Static tracing then confirmed `-DT 1` gates native test-player creation and individual `-Tal/-Buki/-Elco/-Ailish 1` arguments choose actors; the user subsequently confirmed Tal and Ailish both spawned. The current launcher now starts Ailish alone and enables an exact-build F8 overlay for native Tal/Buki/Elco and Training Dummy spawn/despawn. Build and offline ABI/image tests pass; the new menu and dummy behavior await live confirmation.

If the shipped dummy is passive but mortal, the next narrow experiment will track only that entity and reject its terminal damage or restore its HP through a confirmed native API. If it is unsuitable, reuse another existing enemy in this native room before attempting original level authoring. A true custom flat map remains SudekiForge work because it requires confirmed geometry, collision, lighting, visibility, spawn, navigation, trigger, script, and archive formats.

## Multiplayer integration constraints

- The user recalls that spending Spirit Strike power with one character depletes the meter for the whole party; this still needs a controlled gameplay check. Treat SSP as one host-authoritative party resource unless testing or reverse engineering disproves that model. Multiplayer activation must be serialized so simultaneous player requests cannot spend the same meter twice. Whether the value is physically stored once or mirrored between characters remains unconfirmed.
- The shared midpoint camera and maximum-separation rule remain the single-screen fallback. The split-screen branch has distinct assigned Ailish/Buki render states with an alternating one-render-per-frame cache; truly simultaneous same-frame camera rendering remains later work. Per-player zoom limits can be widened later, but must not allow players to escape arena, transition, or scripted-event constraints.
- Title screens, loading screens, ordinary menus, the in-game pause/exit menu, and shared cinematics remain one full-screen presentation by default. The Quit interface now renders once over the frozen last-known Ailish/Buki camera pair and resumes live split gameplay on Back. Apply this explicit shared-layer policy separately to other menus and cinematics as they are encountered.
- Before split-screen or independent player cameras, explicitly test Elco's scoped gun view and Ailish's ranged aiming view when another character is locally controlled. A camera attached to a character model may render that character as hidden, partial arms/weapon, or not at all for other viewports; each viewport therefore needs an explicit local-body visibility and camera-ownership policy.
- Native skill cinematics and Spirit Strikes must not seize every player's camera. The first exact-gated Plasmatica prototype now routes `SetRenderCamera` only to its caster's cached viewport; live testing must establish camera-object update behavior and cleanup before this policy is generalized to every skill or Spirit Strike.
- Doorways and zone changes must not silently drag an exploring human player merely because the vanilla AI catch-up timer expired. First identify the transition trigger and recovery authority, then require all players at the boundary or an explicit group/host commit before the transition takes control.
- Cutscenes may place every party member even when gameplay positions differ. Trace entity identity across at least one scene before deciding whether to retain live actors, create scene-local stand-ins, hide absent players, or temporarily transfer control to the scene system.
